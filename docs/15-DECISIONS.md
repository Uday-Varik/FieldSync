# FieldSync — Decisions Log (DECISIONS.md)

Rule from `08-IMPLEMENTATION-PLAN.md`: every deviation from the
planning pack is logged here with date + reason, so "why did you
do it that way?" never becomes a guess. Locked decisions from
2026-10-27 (pdf-lib, Admin reopen with reason, technicians see
assigned jobs only, Clerk not Auth.js, Mapbox, per-mutation sync
transactions) are in `00-INDEX.md` and are NOT deviations — they
are not repeated here except where implementation changed them.

## 2026-10-27 — pnpm replaced by npm

- Deviation: pack originally said pnpm; scaffold and plan now use
  npm workspaces.
- Reason: pnpm is not installed in this environment; npm is, and
  the scaffold was built with npm. Recorded in the Phase 0 audit.

## 2026-10-27/28 — Signature: unique-on-jobId removed

- Deviation: data model originally allowed only one Signature row
  per job (unique on `jobId`).
- Reason: that design makes Admin reopen + re-complete impossible
  (a second signature cannot be stored). Changed to multiple rows
  per job with exactly one current (`isCurrent`, `supersededAt`).
  On reopen, the current signature is superseded, not deleted.

## 2026-10-28 — Seed counts corrected

- Deviation: early seed outline claimed "2 overdue" jobs and photos
  on every completed job.
- Reason: those claims were not in the seed spec. Corrected to:
  at least 1 guaranteed past-date SCHEDULED job (overdue is not an
  exact count), and photos + signature + job sheet on one completed
  job only. Verified counts: 5 users, 18 jobs with the documented
  status breakdown.

## 2026-10-28 — Husky not installed

- Deviation: Phase 0 tooling lists Husky pre-commit (lint +
  typecheck).
- Reason: the workspace was not a git repo when the scaffold was
  built, so Husky was not faked in. It remains outstanding and is
  why Phase 0 is marked partial in `16-PROJECT-TRACKING.md`, not
  fully done. ESLint + Prettier configs do exist.

## 2026-10-28 — Docker replaced by apt Postgres/Redis in this VM

- Deviation: Phase 0 DoD says `docker compose up` runs Postgres +
  Redis.
- Reason: Docker is not installed in this VM. System Postgres 16
  + Redis 7 were installed via apt and started manually, matching
  the docker-compose versions. `docker-compose.yml` in the repo is
  unchanged and remains the correct route on a developer machine.
  This is a VM workaround, not a repo change.

## 2026-10-28 — Prisma engines via a local curl mirror

- Deviation: `npm install` / `prisma validate` normally download
  Prisma engine binaries through Node.
- Reason: Node downloads through the proxy kept resetting
  (ECONNRESET), while curl through the same proxy worked. Engines
  were downloaded with curl and served from a local mirror
  (`PRISMA_ENGINES_MIRROR=http://localhost:8765`). VM workaround
  only, not a repo change, and no proxy credentials were recorded.

## 2026-10-28 — Local test DB user granted CREATEDB

- Deviation: none in the repo; a local-only database permission.
- Reason: first `prisma migrate dev` failed with P3014 (shadow
  database: permission denied to create database). Fixed by
  granting the local test user CREATEDB. Do not hand-write
  migration SQL; migrations are still generated by Prisma.

## 2026-10-28 — `@nestjs/platform-express` added to the API

- Deviation: Phase 0 scaffold shipped without it.
- Reason: Nest compiled, then failed at startup with "No driver
  (HTTP) has been selected". The missing dependency was a real
  scaffold bug, fixed in PR #1, not worked around.

## 2026-10-28 — Independent feature branches, then rebasing

- Deviation: Phase 1 branches were each created from `main` after
  PR #2, independently, instead of sequentially on top of each
  other.
- Reason: that kept each PR reviewable on its own, per the
  branch-per-feature rule. Consequence, recorded honestly: PR #4
  (jobs) and PR #5 (checklist) both edited `app.module.ts` on the
  same line as PR #3 (companies), so they conflicted after PR #3
  merged, and GitHub's "update branch" also failed on the conflict.
- Fix, 2026-10-29: PR #4 was closed and superseded by PR #7 (jobs
  rebased on PR #3, app.module keeps Companies + Jobs); PR #5 was
  closed and superseded by PR #8 (checklist rebased on PR #7,
  app.module keeps Companies + Jobs + Checklist). Both rebased PRs
  merged cleanly. Lesson for later phases: when branches share an
  integration point, sequence them (rebase on the merged branch)
  instead of branching them all from the same base.

## 2026-10-28 — Company creation: email/name come from Clerk

- Deviation: API spec body for `POST /companies` is only
  `{ name, timezone }`, with no email/name for the new user row.
- Reason: the FieldSync User row requires email + name, and those
  must not come from a client-supplied body (a client could claim
  someone else's email). `ClerkService.getProfile()` loads them
  from Clerk for the verified user id. Same pattern is used, as a
  fallback, in invite accept.

## 2026-10-28 — Invites: no email sending yet

- Deviation: invite flow in a full product emails the invite link.
- Reason: no email service is in MVP scope for Phase 1. The raw
  token is returned exactly once at creation (only its SHA-256 hash
  is stored), and the caller must deliver it. Email delivery is a
  later slice, listed as outstanding in the tracking doc.

## 2026-10-28 — Status endpoint rejects CANCELLED

- Deviation: the state machine lists CANCELLED as a valid next
  status from most states, which could suggest cancelling through
  `POST /jobs/:id/status`.
- Reason: the spec gives cancel its own endpoint with a required
  reason. Allowing CANCELLED through the status endpoint would let
  callers bypass the reason requirement, so the status endpoint
  returns 422 for CANCELLED and directs callers to the cancel
  endpoint.

## 2026-10-28 — Checklist toggle: Admin also allowed

- Deviation: API spec says toggle is "Assigned technician or
  Dispatcher".
- Reason: a strict reading would lock an Admin out of a job they
  manage. Admin is allowed as supervisor; the assigned-only rule
  for Technicians is unchanged, and company scoping is unchanged.

## 2026-10-28 — Web auth: typecheck only, dashboard shell only

- Deviation: Phase 1 web work is the dispatcher board and the
  technician My Day list.
- Reason: the web-auth slice (PR #6) was deliberately scoped to
  Clerk provider, middleware, sign-in/up pages, and a `/me`
  dashboard shell, so the board/My Day screens can build on a
  working auth chain. Live web testing was not faked: it needs
  real Clerk keys and a running API, both outstanding, so only
  typecheck is claimed as verified for this slice.

## 2026-10-28 — Manager role "Sundar" added (not in the pack)

- Deviation: no manager role exists in the planning pack.
- Reason: user request, 2026-10-28, repeated as "always keep
  Sundar active". Sundar is a FieldSync-only role name (not the
  real Sundar Pichai), owning the quality gate, batching decisions
  to one approval per major step, and reducing interruptions.
  Limit, recorded in `14-PROJECT-MANAGER.md`: Sundar cannot
  approve runtime permission cards, GitHub writes, purchases, or
  other consequential actions — those remain the user's, and the
  user's own "always allow" choice on a card is the only way to
  skip future cards of that kind.

## 2026-10-29 — Tracking: PROJECTS.md chosen over GitHub Issues

- Choice, not a deviation: the plan allows "GitHub Issues (or a
  simple PROJECTS.md)".
- Reason: tracking lives in the repo in `16-PROJECT-TRACKING.md`,
  one task per plan task, phase-labelled, with DoD/test status,
  so it is reviewable in the same PR flow and does not need a
  separate approval card per issue. It can be migrated to GitHub
  Issues later without changing the task list. An issue/task is
  closed only when its DoD + tests are met — see the tracking doc
  for the partial Phase 0 and partial Phase 1 audit-log items,
  which are deliberately left open.

## Timebox rule (from the plan, applied going forward)

- If stuck for more than 2 hours on one task, timebox it, write
  the blocker in the tracking doc, and move to an independent
  task. In particular, do not let sync (Phase 4) or Yjs (Phase 3)
  block the whole build.
- Blockers already logged this way: real Clerk keys, Mapbox token,
  S3/R2 bucket, Husky, and a running Postgres/Redis in this VM
  (wiped by VM restarts). None of these were faked to claim a
  live test as passed.

## 2026-10-29 — Audit log: service-level events, not a global interceptor

- Deviation: Phase 1 lists "Audit log (interceptor/event)".
- Reason: JobActivity is written by the services in the same
  transaction as the job change (create, status, assign, cancel,
  reopen, checklist toggle), and the timeline is shown on the job
  detail page (`/jobs/[id]`). A global post-response HTTP
  interceptor would duplicate those rows and would not be
  transactional, so it was not built. The DoD item — "audit
  timeline shows on job detail" — is met by the service-level
  events, and the tracking doc records this reasoning.

## 2026-10-29 — Phase 1 board/My Day scope

- Board: desktop, grouped by status, search + status filter,
  manual refresh only. No map and no realtime in Phase 1, per the
  plan; both are Phase 3 work and must replace manual refresh then.
- My Day: read-only, online only, today's jobs in
  America/Chicago. Checklist toggles, status actions, photos, and
  signature for technicians are Phase 2, so they are hidden for
  technicians in Phase 1 UI even though the API allows assigned
  technicians to change status.
- Create-job form: technician id is a text field, because no
  /users list endpoint exists yet in Phase 1. A users list is a
  Phase 2 improvement, not a Phase 1 blocker.

## 2026-10-29 — Phase 2: PDF generated on demand, not at completion

- Deviation: the plan says the job sheet PDF is generated on
  COMPLETED. In PR #15 it is generated on demand at the first
  download of a completed job's sheet, and the JobSheet row is
  then marked READY with generatedAt.
- Reason: there is no S3 storage or background queue yet to
  store a PDF at completion time. On-demand generation meets
  the download endpoint requirement without inventing storage.

## 2026-10-29 — Phase 2: photos without thumbnails or client compression

- Deviation: PR #16 ships signed upload, confirm, grid, and
  soft delete, but no BullMQ thumbnail job and no client-side
  image compression.
- Reason: thumbnails need a running Redis + a bucket, both
  still outstanding, and compression is a client optimisation
  that must not block the upload flow. The grid shows the
  original image until the thumbnail slice lands. If storage
  is not configured at all, upload URLs return 503
  STORAGE_NOT_CONFIGURED instead of faking a photo.

## 2026-10-29 — Phase 2 fix: thumbnails with BullMQ + Jimp, best-effort queue

- Thumbnail job: BullMQ queue `thumbnails`, worker run
  separately (`npm run worker:thumbnails`). Enqueue is
  best-effort: with no Redis configured it returns false,
  and a Redis outage never fails a photo confirm.
- Jimp (pure JS) instead of sharp for resizing: no native
  binary download, after the Phase 0 Prisma-engine download
  trouble. Jest runs under node --experimental-vm-modules
  because Jimp v1 is ESM — without it the thumbnail tests
  fail with a dynamic-import error.
- Client compression: canvas resize to at most 1600px as
  JPEG 0.8 before upload, falling back to the original file
  if compression fails.

## 2026-10-30 — Phase 3: realtime, map, Yjs; web-upload fallback for the Yjs slice

- Realtime: single API instance, no Redis adapter in MVP
  (scaling step, not a Phase 3 requirement). Emits happen
  after the DB transaction commits, so a board refresh
  cannot race a commit. @nestjs/websockets pinned to v10
  (v12 requires Nest 12).
- Map: jobs without stored coordinates are geocoded
  client-side on view; server geocoding on create is
  best-effort (MAPBOX_TOKEN). Without a token the map
  page shows a list instead of a broken map.
- Yjs: snapshot persistence via JobNoteDocument, not a
  separate Yjs persistence server; y-websocket is used
  only when NEXT_PUBLIC_YJS_WS_URL is set.
- Yjs files landed via the GitHub web upload UI, not
  the connector push: five connector push approval cards
  timed out (60 minutes each, no decision), and one
  Allowed decision arrived after its waiting process
  had been killed by a restart. package-lock.json was
  not updated in that upload and must be regenerated
  with npm install before npm ci is used.

- Sync idempotency checked BEFORE authorisation (2026-10-30):
  a replayed batch must return the stored result even if
  the job has since been cancelled; checking authorisation
  first would turn an applied change into a rejection and
  duplicate audit entries on replay. The stored result
  leaks nothing new to a removed user.
- Sync checklist/note/signature/photo mutations bump Job.version
  (2026-10-30): the REST checklist toggle does not bump the
  job version, but sync-applied mutations bump it so the
  client's clientVersion tracks sync-applied changes.
- Offline photos: ADD_PHOTO_META creates a PENDING Photo row;
  upload-url accepts the same storageKey only when a PENDING
  row exists for that job; confirm reuses that row instead
  of creating a duplicate (2026-10-30). Photo upload retry
  is separate from job field sync: a failed binary upload
  leaves the blob PENDING and never fails the metadata sync.
- Conflict UX: technician banner text is generated from
  conflictDetails, not hardcoded; rejected outbox items
  offer Discard only, never Retry (server rejections are
  not transient). Dispatcher timeline shows offline sync
  entries with conflict details inline (2026-10-30).
- Connector push for the conflict-photos slice was killed
  by a service restart mid-call; the commit (d39cab8f)
  had already landed, verified by remote readback before
  the PR was created — no duplicate push was sent.
- Live verification, VM-only workaround (2026-10-31):

- Deviation: `docs/06` said "Tailwind + a small set of shared
  components is enough". The Tailwind half no longer stands:
  slice (a) ships one `globals.css` (CSS custom-property

  `components/ui/` in this slice; the remaining shared

- Token adjustment in slice (a): `--color-border-strong`

## 2026-11-01 — My Day orders today's jobs by window start in the page (UI Redesign slice (b))

- Deviation: `docs/17` §4 slice (b) said My Day grouping should
  use "the order the API returns plus the overdue flag" and "do
  not silently re-sort" if API order is not window order. The
  API returns `scheduledDate` asc, then `createdAt` desc — not
  window order — while `docs/06` S20 / `docs/11` S20 require
  "Today (in window order)". Slice (b) therefore sorts the
  already-returned same-day jobs by `scheduledWindowStart` in
  the page (stable sort: ties keep API order), using only
  fields the list endpoint already returns. No API change, no
  new sort contract on the server; the sort is stated in the
  slice (b) PR description, not silent.
- Related limit, not a deviation: My Day keeps the existing
  `date=today` query, so its Overdue group covers only today's
  jobs whose window end has passed. Past-date overdue jobs are
  not returned by that query; showing them would need a query
  change (e.g. `dateFrom`), deferred — widening the query under
  `limit=100` could push today's jobs out of the page.

## 2026-11-01 — Job detail + creation presentation decisions (UI Redesign slice (c))

- Shared components created in this slice as first use, per
  the slice (a) deferral note: `Button`, `Field`, `Banner`,
  and `ConfirmBlock` under `components/ui/`. No unused
  shared component ships; `Card` remains unused and is not
  created (detail sections use their own module styles).
- Not a deviation: status moves are NOT confirmed. The
  confirmation list in `docs/17` §3.3 and `docs/06`
  principle 4 is Cancel / Delete photo / Reopen — status
  moves stay immediate, with busy/disabled states added.
  Cancel and Reopen confirm inline, reusing the existing
  reason field; the confirm step is disabled until a reason
  is entered, because the API requires one (an empty reason
  previously posted and failed server-side — same endpoint
  and payload, the failing post is simply not sent).
- Photo caption field deferred, not faked: the confirm
  endpoint accepts `caption`, but the offline queue path
  (`storeOfflinePhoto` / `ADD_PHOTO_META`) carries no
  caption, so a caption entered online would silently
  vanish offline. Adding one needs a sync-worker/outbox
  change, out of scope for a presentation slice.
- Audit timeline limits, from the data the API returns:
  activity rows carry `actorId` only, so no actor name is
  shown and none is invented; entries keep the order the
  API returns (newest first); note text is never quoted
  (NOTE_UPDATED rows keep the previous text in `fromValue`
  for the record, the timeline says the notes changed).
  Status codes are humanised with the shared labels;
  conflict rule codes are removed from user view.
- The assigned technician has no name in the data
  `GET /jobs/:id` returns (only `assignedTechnicianId`),
  so the detail page shows "Assigned technician ID" with
  the id, or "Unassigned" — no name is invented. This
  matches the create form, where dispatchers paste the
  same id because no users-list endpoint exists.
- The sticky technician bar keeps its existing place in
  the page flow (after contact actions) and gains
  `position: sticky; bottom:` styling, so the actions
  stay at thumb reach while scrolling (docs/06 S21).
  Completed/cancelled jobs now show their state in the
  bar instead of the section vanishing.
